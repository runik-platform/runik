# MongoDB glyph design

The `mongodb` glyph separates two independent concerns:

- Percona Server for MongoDB owns physical clusters, TLS, storage, replication,
  backups and restores.
- `mongodb-operations` owns logical engine registration, databases and users for
  any MongoDB-compatible server.

It does not provision collections. MongoDB materializes collections on first
use and the database is the authorization boundary exposed to applications.

## Ownership model

The physical engine spell publishes one `type: mongodb` lexicon entry. That
entry associates application databases with an engine and carries only the
connection coordinates applications need: `engineName`, cluster name,
namespace, host, port, replica set and TLS state.

Databases and users are Kubernetes CRs and are not published through the
lexicon. Librarian contains no MongoDB-specific behavior.

The resource chain is:

```text
PerconaServerMongoDB (optional physical implementation)
  └─ MongoDBEngine (cluster-scoped administrative connection)
       └─ MongoDBDatabase (namespaced logical boundary)
            └─ MongoDBUser (one database + one credential Secret)
```

References are logical rather than Kubernetes owner references. Removal order
is User, Database, then Engine so user finalizers retain access to the
administrative connection.

## Physical Percona cluster

```yaml
mongodb:
  mongo-main:
    type: cluster
    namespace: databases
    storage:
      size: 20Gi
    operations:
      allowedNamespaces:
        matchLabels:
          mongodb.runik.io/engine: mongo-main
```

When `operations` is present, `mongodb.cluster` renders:

- one `PerconaServerMongoDB`;
- one stable administrative credential Secret;
- one Percona administrative user scoped to user/database administration;
- one `MongoDBEngine` referencing that Secret and Percona's generated CA;
- an S3 backup identity and scheduled backup configuration unless disabled.

The administrative user has `userAdminAnyDatabase` so it can reconcile users
and `dbAdminAnyDatabase` so an explicitly confirmed Database/Delete can execute
`dropDatabase`. Applications never receive these credentials.

`operations.allowedNamespaces` is required. The engine never defaults to all
namespaces. The normal policy selects a namespace label managed through the
spell's `appParams.managedNamespaceMetadata`.

Backups are enabled by default and run every Sunday at 03:00 with `0 3 * * 0`.
Every enabled task requires a schedule. There is no on-demand backup glyph; a
restore remains an explicit one-shot disaster-recovery operation.

No bootstrap Job is rendered. Percona creates the administrative identity from
`spec.users` and the logical operator uses normal MongoDB commands for users.

## Generic engine primitive

`mongodb.engine` registers an existing MongoDB-compatible server:

```yaml
mongodb:
  shared:
    type: engine
    connection:
      uri: mongodb://mongodb.database-system.svc.cluster.local:27017
      authenticationDatabase: admin
      credentialsSecretRef:
        namespace: database-system
        name: mongodb-operator-admin
        usernameKey: username
        passwordKey: password
      tls:
        enabled: true
        caRef:
          kind: Secret
          namespace: database-system
          name: mongodb-ca
          key: ca.crt
    allowedNamespaces:
      matchNames: [orders]
```

The URI is credential-free. Credentials and CA material are always references.
This primitive does not know whether the Secret was generated by Vault,
External Secrets or another system.

## Application database meta glyph

```yaml
mongodb:
  orders:
    type: database
    defaultUser:
      access: readWrite

vault:
  orders:
    type: prolicy
```

For external-chart or path spells, put both blocks under `glyphs:`. For summon
spells, keep them at the spell root.

`mongodb.database` renders:

1. `MongoDBDatabase/orders`, defaulting to `deletionPolicy: Retain`;
2. a stable Vault-generated Secret when credential generation is enabled;
3. `MongoDBUser/orders`, defaulting to `readWrite` and User/Delete.

The supported presets map as follows:

| Preset | MongoDB roles on the selected database |
|---|---|
| `readOnly` | `read` |
| `readWrite` | `readWrite` |
| `schemaAdmin` | `readWrite` + `dbAdmin` |
| `owner` | `dbOwner` |

`owner` is exceptional because `dbOwner` includes user administration. The
operator replaces the user's exact role set with the selected preset; stale or
cross-database roles are removed.

Set `defaultUser.enabled: false` for a database without its conventional user.
Additional database-scoped identities use the `mongodb.user` primitive.

## Credentials and rotation

The operator only reads `credentialsSecretRef`. The normal glyph composition
uses Vault RandomSecret/VaultSecret to produce a stable Secret containing
`USERNAME`, `PASSWORD`, `HOST`, `PORT`, `DATABASE`, `AUTH_DATABASE`,
`REPLICA_SET` and `TLS`. Applications may map the same keys into environment
variables or mount them as files.

Set `credentials.generate: false` to reference an externally managed Secret.
No Reloader, generated ConfigMap or automatic Pod restart is part of this
design.

Password rotation is deliberately two-phase:

1. change the external Secret and wait for its new value;
2. advance `MongoDBUser.spec.credentialsRevision`.

For Vault-generated values, `credentials.generationRevision` changes the
RandomSecret/VaultSecret source but keeps the output Secret name stable. Sync
that change and verify the Secret before advancing `credentialsRevision`. This
ordering prevents the controller from recording a new revision while the old
password is still present asynchronously.

Changing a Secret without advancing `credentialsRevision` never rotates the
MongoDB password. Changing the username of an existing user is rejected; create
a new `MongoDBUser` identity instead.

## Deletion

Users default to `Delete`, so removing their CR drops the database-scoped user.
Databases default to `Retain`. Destructive removal requires both
`deletionPolicy: Delete` and `allowDrop: true`, which renders the operator's
`mongodb.example.io/allow-drop-database=true` confirmation annotation.

`mongodb.instance` remains the escape hatch for a complete native Percona spec.
`mongodb.restore` renders `PerconaServerMongoDBRestore` because restoration is
an explicit disaster-recovery operation rather than a recurring schedule.

## Distribution

`charts/glyphs/` is the canonical glyph worktree. Consumers (`charts/kaster/`,
`charts/summon/`, `charts/trinkets/microspell/`, `charts/trinkets/tarot/` and
`covenant/`) pin the same `glyphs.git` repository as submodules. Ship glyph
changes by merging the canonical worktree into `glyphs/upstream`; the
operational Tarot release reading bumps every consumer and the Runik aggregate.
See `creating-glyphs.md` for the automated path and manual recovery checklist.
